# Better Auth を使う場合との比較（2026-08-14）

**日付**: 2026-08-14  
**対象**: astro-user-webauthn プロジェクト  
**比較対象**: [Better Auth](https://www.better-auth.com/)（TypeScript 向け認証ライブラリ）

## 概要

本ドキュメントは、現行の自前認証を [Better Auth](https://www.better-auth.com/) に置き換えた場合に何が得られるか、何が失われるか、現状仕様を維持できるかを比較したレビューである。仕様の正本は [specification.md](../specification.md) である。

## 結論

現状の仕様を維持するなら、Better Auth への載せ替えは投資対効果が低い。

Better Auth はパスワード・マジックリンク・パスキー・OAuth などをプラグインで足せる汎用の認証基盤である。本アプリの価値は、その汎用セットではなく、招待制パスキー移行の状態遷移と制約の組み合わせにある。同じ制約を Better Auth で再現するには hook の後付けが必要で、独自仕様のコード量はあまり減らない。一方でスキーマ・ルーティング・結合テストは大きく書き換わる。

## 比較の前提

本アプリの認証は次のライフサイクルで固定されている。

```text
未登録 → 管理者招待（User 作成）→ 初回だけメール証明 → パスキー必須
     → 以降はパスキーのみ → 詰まったら全パスキー破棄の復旧
```

Better Auth の既定は「ログイン手段を並べて、ユーザーが選べる」である。パスキーは追加手段であり、登録後に他手段を自動では閉じない。マジックリンクは「クリック＝ログイン」が既定である。

## 項目別比較

### 1. 認証モデル

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| 位置づけ | パスキー必須の閉鎖系。手段はライフサイクルの段階 | 手段の集合。プラグインで足す |
| パスキー登録後 | パスワード・マジックリンクを拒否 | 他手段は残る。閉じるなら `before` hook |
| 自己登録 | なし。管理者が User を先に作る | 既定は自己登録あり。`disableSignUp` 等で制限 |
| 初回ログイン | 招待マジックリンク（seed 管理者のみパスワード） | 汎用マジックリンク／パスワード／パスキー |

現行の方が、メール侵害後も日常ログインを取れない、という脅威モデルが一本になっている。Better Auth で同じことをするには、政策を hook で再現する必要がある。

### 2. メールとトークン消費

| 事象 | 現行実装 | Better Auth 既定 |
|------|----------|------------------|
| パスキー登録後のメール侵害 | 日常ログイン不可 | マジックリンクで入れることが多い |
| デバイス招待リンクの漏洩 | パスキー追加の可能性。セッションは付かない | 同等の「ログインしない登録」は標準にない |
| メールクライアントの GET プリフェッチ | トークンは残る（確認ボタンの POST で消費） | verify の GET で消費・ログインしうる |

現行はメールをオンボーディングと復旧のチャネルに限定している。Better Auth のマジックリンクは継続的なログイン手段である。デバイス追加の「再認証＋メール招待、クリックではログインしない」は、`registration.requireSession: false` と `resolveUser` で近づけるが、再認証フラグ・TTL・ハッシュ化トークン・メール本文は自前のまま残る。

### 3. 復旧

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| 最後のパスキー削除 | 不可。復旧はパスワード再設定に一本化 | パスキー削除は標準 API。最後の 1 件制限は自前 |
| パスワード再設定時 | 全 Credential 削除、全 Session 失効、未使用招待無効化、自動ログイン、パスキー再登録必須 | パスワード更新が中心。既存パスキーは残りやすい |
| UI | 「全パスキー無効化」を警告 | 同等の警告・一括破棄は after hook で追加 |

現行は 1 台紛失時に「全部捨てて出直す」が明確である。Better Auth ではメールとパスキーが並立したままになりやすい。

### 4. データ配置とセッション

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| PostgreSQL | User / WebAuthnCredential / Post | `user` / `session` / `account` / `verification` / `passkey` を持ちたがる |
| Redis | Session・challenge・招待・再設定・レート制限（TTL、使ったら削除） | 二次ストレージ。セッションはキャッシュ寄り |
| セッション値 | `{ id, userId, createdAt }`。ロール等は毎回 PostgreSQL | セッションにユーザー情報を載せることが多い |
| 失効 | キー削除。`usedAt` / `revokedAt` なし | DB レコード＋二次ストレージ。プラグイン利用時は session テーブル残置が必要になりうる |

現行の方が、短命トークンとドメインデータの境界がはっきりしている。Redis 再起動で未使用トークンが消えることは、仕様として受け入れ済みである。Better Auth に載せると Prisma スキーマの所有権が認証ライブラリ側に寄る。

### 5. アプリ構造

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| API | Hono の `/auth` `/admin` `/devices` `/posts` | catch-all の `/api/auth/*` が中心 |
| ページ認可 | `getPageSession` / `redirectForAuth` | `auth.api.getSession` と Astro locals |
| ブラウザ | `src/api-client` | `createAuthClient`（React 向けクライアントあり） |
| スキーマ | Prisma のドメインモデル | CLI によるスキーマ生成・マイグレーション |
| テスト | 仕様の政策を結合テストが直接検証 | ライブラリ既定＋hook の挙動にテストを合わせる |

現行は認証がアプリの形に従っている。Better Auth は認証がルートとスキーマを引き取る。クライアント SDK と Conditional UI（ブラウザ自動補完）は Better Auth 側が強い。

### 6. 保守と拡張

| 項目 | 現行実装 | Better Auth を使う場合 |
|------|----------|------------------------|
| WebAuthn | `@simplewebauthn` を直接利用 | 内部は同じく SimpleWebAuthn |
| セキュリティパッチ | 自前（セッション、CSRF、レート制限、トークン設計） | ライブラリ側に寄せられる |
| 管理者機能 | 招待・一覧・ロール（admin / user） | ban、impersonate、セッション一覧・失効が標準 |
| 将来の手段 | 仕様を変えない限り足さない | OAuth、2FA、Organization、SSO を足しやすい |
| ロックイン | 仕様とコードがリポジトリ内 | バージョンアップとプラグイン互換に依存 |

パスキー実装そのものを買い直すわけではない。買うのは汎用の認証プロダクトとエコシステムである。

## 載せ替えた場合に残る自前コード

現状仕様を保つなら、Better Auth 導入後も次は hook または周辺実装として残る。

- パスキー登録後のパスワード／マジックリンク拒否
- パスキー未設定セッションの setup / logout / me 以外拒否
- 招待専用マジックリンク（GET 非消費、POST 消費、パスキー済み拒否）
- デバイス招待（再認証必須、ログインしない登録）
- パスワード再設定時の全パスキー削除と全セッション失効
- 最後のパスキー削除禁止

結果として「ライブラリ＋厚い hook 層」になり、独自仕様の核は自前のまま残る。

## 判断

| 状況 | 判断 |
|------|------|
| 今の仕様を保つプロトタイプ／学習用 | 載せ替えない |
| パスキー必須・招待制・デバイス招待を製品の差別化にする | 現行のまま仕様を固める |
| OAuth・2FA・組織・なりすましなど汎用認証を足す | Better Auth の利点が出る。その時点で再検討する |
| 認証のセキュリティ保守を外に出したいだけ | 利点はあるが、この仕様を hook で再現するコストの方が大きい |

現状の仕様（招待制・パスキー必須・デバイス招待はログインしない・復旧は全パスキー破棄）を保つ限り、現行設計を維持した方が制御しやすい。
